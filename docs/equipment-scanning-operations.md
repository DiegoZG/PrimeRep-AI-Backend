# Equipment scanning and OpenAI operations

The implementation uses the existing PrimeRep catalog and preserves every equipment/exercise identity, favorite, workout/session history and existing API. New routes, DTOs and recovery semantics are defined in [equipment-scanning-contract.md](equipment-scanning-contract.md). The `RecognitionAdapter` and `CatalogRepository` boundaries keep recognition observations separate from database/public identities. OpenAI supplies no stable equipment IDs, so this slice adds no invented provider mapping table or automatic identity merge.

## Provider configuration and cost admission

The selected candidate for both chat and image recognition is `gpt-6-luna`, independently configured by `OPENAI_CHAT_MODEL` and `OPENAI_VISION_MODEL`. Reasoning defaults to `none`; only `none|low` is allowed. SDK `openai==2.8.1` was inspected on Python 3.9.6: `Responses.create/parse`, `text_format`, `max_output_tokens`, `reasoning`, `store`, Standard `service_tier` and explicit timeout are supported. Every SDK client sets `max_retries=0`; no paid fallback, quality escalation or automatic inference retry exists. Existing exercise Q&A, coach week/day generation and safe categorical Coach feed wording use the shared adapter. Coach feed remains selection among existing safe wording variants; it does not generate arbitrary recommendations. The retired draft-content script uses the same boundary and still cannot publish.

The existing Passlib password backend is preserved with `bcrypt==3.2.2`, matching the previously working environment. A clean install otherwise selected bcrypt 5, whose changed long-password handling breaks Passlib's backend self-test even for ordinary signup passwords. No password/authentication logic or historical hashes are rewritten.

Safe placeholders are in `.env.example`. The shared application budget defaults to a configurable USD 10 lifetime test cap, USD 10 daily cap and USD 10 monthly cap per deployment database/environment, across all OpenAI chat/draft/scan workloads. This does not buy provider credit, create a provider hard spending limit, or authorize an automated live call. Separate deployments/databases require coordinated operator caps; this ledger is not cross-database accounting.

PostgreSQL transaction-scoped advisory locking serializes budget reservation across replicas. The same short transaction reserves accepted scan quota and receipt state; no financial/catalog/subscription lock is held across image upload or provider calls. The priced allowlist currently contains only verified `gpt-6-luna`; an unknown model or invalid/zero budget configuration fails closed before inference. Changing a model requires reviewing and adding its pricing/context bounds first.

Verified official Standard short-context rates are USD 0.10 input / USD 0.50 output per million tokens; above 272K input the documented rates increase. Reservations include full uncached input, cache-write headroom, long-context multipliers where applicable, and the bounded output (which includes reasoning tokens). Text input is bounded by UTF-8/schema bytes plus framing headroom. Since this candidate's exact image-token resizing multiplier has not been benchmarked, vision reserves conservatively against its entire documented context ceiling, approximately USD 0.263076 for the current 768-output-token cap; measured known usage then reduces that reservation to conservative accounted usage. This is deliberately an upper-bound admission mechanism, not an invoice claim or estimate of typical scan cost.

Timeouts, cancellation and unknown/malformed usage retain the full conservative reservation. Known usage is accounted even when subsequent domain validation fails. Moderation-only rejection never starts paid recognition and settles that recognition reservation at known zero; accepted attempt quota is still consumed. Missing settlement/storage service leaves the previously reserved amount held. Neither receipt pruning nor account deletion refunds unknown provider charges. No automatic reconciliation invents a zero bill.

```bash
python -m scripts.equipment_scanning budget
python -m scripts.equipment_scanning prune
```

`budget` prints only period/cost totals and unsettled counts, never account/attempt IDs, prompts, images or credentials. Operator reconciliation of uncertain charges is manual against provider usage before any deliberate ledger adjustment; this slice has no automated refund command. Provider-console alerts are supplemental, not a hard application stop.

Official sources checked during implementation: [Luna capabilities/pricing](https://developers.openai.com/api/docs/models/gpt-6-luna), [Python Responses API](https://developers.openai.com/api/reference/python/resources/responses/methods/create), [image sizing/billing](https://developers.openai.com/api/docs/guides/images-vision), and [moderation category coverage](https://developers.openai.com/api/docs/guides/moderation). Model availability was checked with one separately authorized read-only models request. No inference or image transmission is implied by that check.

## Safety, privacy and retention

A scan accepts one raw JPEG/PNG, actual decoded format matching its MIME, at most 5 MiB received bytes, 20 million decoded pixels and one frame. Upload reading has an eight-second deadline, byte buffers clear on every exit, and the authorization read transaction ends before waiting for body bytes. CPU-heavy orientation/decode/re-encoding runs off the event loop with two nonblocking normalization slots per worker. The initial candidate is 1024 px longest edge / JPEG quality 80 (never upscale or square-crop); the configurable ceiling is 1536. These are evaluation settings, not a validated accuracy result.

The normalized image is screened by `omni-moderation-latest` before one combined primary-subject/recognition request. Moderation failure never bypasses screening, and moderation rejection prevents recognition. Moderation does not establish gym-equipment presence or detect all harmful categories; the official service has image-specific category limits and is not a CSAM handling/detection substitute. Recognition handles unrelated/unclear/multiple-primary subjects with fixed no-match reasons. It has no browsing/tools, image Q&A, arbitrary guidance generation or provider exercise/media URLs.

PrimeRep does not store or log the photo, OCR/image text or raw provider output. Metadata is removed during normalization; image data remains request-local memory, not an avatar bucket or upload file. OpenAI and underlying HTTP SDK payload/debug loggers are explicitly suppressed, including when a debugging environment variable was set before import; application exceptions/errors are fixed safe categories. Do not override that protection with custom wire/body logging. `store=False` controls response storage but is not a provider zero-retention promise. The app disclosure must explain external OpenAI processing and applicable provider retention/training terms before production photo upload is enabled.

Account/environment-scoped HMAC fingerprints and versioned receipts expire after fifteen minutes and are never shared across owners. Published availability is revalidated on current guidance reads; old receipts cannot permanently authorize media. Owned receipts/quota rows cascade on account deletion; deletion during recognition is rechecked before result persistence. Account export includes explicit unexpired receipt/result/error metadata without photos, internal fingerprints, provider bodies or prompts. The global financial ledger has no owner identity and remains independent of receipt deletion.

Configure and monitor a per-minute `python -m scripts.equipment_scanning prune` job for expired receipts/fingerprints and expired quota counters. Receipt API visibility expires at fifteen minutes even if physical pruning is delayed; document and monitor that deletion lag. Quota counters outlive the receipt window so pruning cannot reset the daily allowance. Existing workout diagnostic retention remains a separate job/contract.

## Admission, recovery and rollback

Scanning is independently default off through `equipment_scanning_enabled`, using existing global/selected-user/override/audit controls. Verified active/trial/grace access or a valid existing grant permits scanning; legacy training admission with enforcement off does not make scans free. Old expired positive verification is unknown (503/check/retry), not a claim that a subscription is missing; a fresh verified negative is 403. Manual search and currently published guidance remain available without scan access or scan enablement.

Accepted pilot limits are configurable: three per rolling minute, twenty per UTC day, two globally processing scans. PostgreSQL protects admission across workers/devices; no in-memory quota authorizes provider work. Invalid submissions also face a shared route-abuse limiter. Accepted blocked/no-match/failed attempts consume quota. Same-key or current same-image receipt reuse does not reserve another provider call or consume accepted-attempt quota. Same key with changed normalized content is rejected.

One account's processing or externally unknown attempt blocks another admitted attempt for that account through the receipt window. The unknown response contains the owned attempt key, bounded remaining-window retry metadata and a manual-search path; it does not claim the worker is still running. A deadline-expired worker becomes unknown, releases its global *application concurrency* slot, and retains both deduplication and the full financial hold. Other accounts are not blocked for fifteen minutes solely by two unknown external outcomes. Only genuinely processing attempts count against the global slot; this does not assert that an external bill disappeared.

Read-only Check result never calls a provider. Cancellation does not prove external work or billing stopped. A new inference always requires an explicit user action and fresh admission; no network retry silently sends the photo again. Rollback is checked before admission and again after moderation, before recognition. Existing workout logging, purchases, subscription launch clocks and reliability monitoring are unchanged.

- Plate-loaded: `plate_loaded_seated_calf`, `plate_loaded_t_bar`.

Recognition context is limited to this linked pilot cohort. Unsupported/lookalike plate-loaded machines must not be forced into a selectorized option. Broad cable observations remain ambiguous and require explicit confirmation. All confidence is unknown/null until a held-out study calibrates it. Manual search may show other active equipment with no exercise options; that is truthful. One-to-many options and published/withdrawn guidance are proven with isolated test-only fixtures, not fabricated product approvals.

No held-out photo accuracy, latency, safety or cost-per-useful-match benchmark is claimed. Broad rollout and truthful subscription-teaser availability remain gated on reviewed content/media coverage, consented photo evaluation, provider disclosure/store declarations and operator approval. Keep the flag off after additive backend deployment; begin with explicitly selected synthetic/internal users only. No production deployment or live photo/inference call is authorized by the implementation tests.
