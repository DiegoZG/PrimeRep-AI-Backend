# Part 9 — Production Readiness and Observability

Status: implementation in progress, September 24, 2026, on `feat/production-readiness` in both repositories. Deploy the backward-compatible backend first, then the mobile app. This document does not authorize a public release or represent external approvals as complete.

## Outcome and scope

PrimeRep can be released to an initial group of real users with workout data that survives interruption, a reproducible deployment, working account recovery, actionable failure alerts, and a tested restore path. The initial release target is iOS and Android; the HTTPS password-reset page must work in a browser. If the rest of the web app is publicly exposed, it receives the same online smoke checks, while the native SQLite recovery guarantee remains specific to iOS and Android.

Workout recovery and synchronization are already implemented. Native active workouts use SQLite with ordered pending operations and retries (`PrimeRep-AI/utils/activeWorkoutStore.native.ts`); the backend deduplicates session starts and mutation IDs (`app/models/workout_session.py`, `app/models/workout_session_operation.py`). Part 9 verifies those paths under release conditions and closes a specific remaining gap: a cold start without network currently renders a global offline screen before a saved workout can open (`PrimeRep-AI/app/_layout.tsx`). Password-reset email is currently scheduled as an in-process background task, so a process restart or provider failure can lose delivery (`app/api/v1/auth/router.py`).

The Home dashboard redesign follows the Part 9 reliability baseline in [the roadmap](roadmap.md). Part 7.5 content approval and media production can continue independently.

## Phase 0 — Release inventory and decisions

- Record current `main` revisions, migration head, backend and frontend test baselines, Expo SDK and app IDs, supported platforms, current service ownership, and all production dependencies. Keep test fixtures out of production.
- Write a deployment decision record for the API host, managed PostgreSQL with backup and point-in-time recovery, shared Redis for rate limits, the existing PostgreSQL-backed workers, HTTPS app/reset host, Resend sending domain, optional R2 media host, and monitoring account. Record monthly cost, access owner, region, retention, and restore objective. Initial targets are recovery point within one hour and service restoration within four hours; revise them explicitly if the chosen provider cannot support them.
- Inventory credentials and rotate the Resend key previously shared in the development conversation before production use. Establish separate preview and production credentials. Do not put secrets in Git, EAS `EXPO_PUBLIC_` values, crash reports, or build logs.
- Decide whether a public web workout app is in scope for the first release. If it is, verify online logging and reload behavior; document that web token storage is memory-only (`PrimeRep-AI/services/tokenStorage.web.ts`) and that native offline guarantees do not automatically apply to web.

**Deliverable:** a release inventory and decision record with named owners for infrastructure, legal approval, credentials, and store accounts. **Gate:** no production deployment begins with an unknown data store, backup owner, or environment.

## Phase 1 — Verify workout recovery and close remaining gaps

- Treat the current local-first SQLite queue, persisted workout snapshot, ordered replay, retry state, honest pending/failed UI, backend idempotency, and immutable snapshots as delivered functionality (`PrimeRep-AI/utils/activeWorkoutStore.native.ts`, `app/workout/active.tsx`). Verify them under interruption and release-build conditions, and change only behavior that fails those checks.
- Allow an authenticated user with a saved local workout to reopen that workout after a cold start with no network. Resolve the current `bootstrapError` gate in `PrimeRep-AI/app/_layout.tsx` without allowing an unknown account to read another user's data. Handle expired/revoked credentials by retaining the user's local pending operations until the same identity reauthenticates or the user explicitly chooses an account-data action. Never replay one account's queue under another account.
- Audit each local operation from confirmation through server acknowledgment: set create/edit/delete/restore, notes, feedback, finish, abandon, and retry. Make completion wait for required earlier operations and reconcile with the canonical server session after reconnect. Identify any operation that can be acknowledged twice, dropped, reordered, or left permanently failed without a recovery action.
- Keep account-switch fencing and the existing storage-failure warning. Provide a retry path for recoverable terminal failures and a clear export/support path if local storage itself fails. Do not claim a workout is synchronized until the server confirms it.

**Verification:** on both native platforms, start a workout, disconnect, log sets and notes, force-kill, relaunch still offline, resume and finish, reconnect, and observe exactly one server session with every intended mutation once. Repeat with a network timeout during each mutation, a duplicate response, app backgrounding, account switch, and expired auth. Add focused automated queue/replay tests and a native interruption flow; do not rely only on the existing happy-path Maestro flows. Server regression tests must preserve current replay, unique-active-session, and snapshot behavior (`tests/test_resumable_workouts.py`, `tests/test_workout_editing.py`).

## Phase 2 — Production configuration and deployment

- Create an explicit API deployment recipe and preview environment with the same migration and startup process as production. Use a managed PostgreSQL instance, shared Redis, a bounded worker/process configuration, TLS at the trusted proxy, and a documented secret store. Add readiness checks for the database and critical dependencies while keeping a lightweight liveness check (`app/main.py`). Verify migration permissions, including `pg_trgm`, before deployment.
- Make `APP_ENV` an allowed value rather than letting a typo bypass production guards (`app/core/settings.py`). Fail startup for missing/invalid production JWT and refresh secrets, shared rate-limit storage, sending configuration, trusted HTTPS reset URL, and approved CORS origins. Align `README.md` and `.env.example` with the real setting names. Validate proxy headers and redirect behavior behind the chosen host.
- Configure explicit EAS preview and production environments in `PrimeRep-AI/eas.json`. Require an HTTPS `EXPO_PUBLIC_API_URL` for release builds, set real app links and signing identifiers, and verify that preview builds never point to production by accident (`config/api.ts`, `app.json`). `EXPO_PUBLIC_` values are client-visible; use them only for non-secret configuration. Decide whether EAS Update is part of this release; if enabled, separate preview/production channels and use compatible runtime versions.
- Keep native signing credentials and store access outside the repository. Build a preview binary against preview services before a production/TestFlight or Play internal build. Ensure the browser reset route is reachable from a different device/network and returns users to a usable reset flow.

**Verification:** preflight fails on missing or wrong environment values; deployed API passes liveness/readiness and migrations; preview and production binaries report the intended API host; login, reset, program activation, Coach, profile, and export work against their intended environment. Follow [Expo environment guidance](https://docs.expo.dev/eas/environment-variables/usage/), [EAS build profiles](https://docs.expo.dev/build/eas-json/), and, if enabled, [update channels/runtime compatibility](https://docs.expo.dev/build/updates/). Do not treat simulator builds as substitutes for signed release builds.

## Phase 3 — Reliable email, legal, and external services

- Replace the in-process password-reset delivery task with a small durable outbox using the existing Coach notification worker pattern as a reference (`app/core/coach_notification_service.py`). Persist only an encrypted short-lived email payload; never log the reset URL or raw token. Retry transient Resend failures with a bound, stop before token expiry, and purge delivered or expired payloads. Preserve the same generic response for known and unknown addresses.
- Verify a domain owned by PrimeRep in Resend; use an address on that domain and check delivery, SPF/DKIM/DMARC configuration, bounce handling, and alerting. Rotate the previously exposed development API key. Test the HTTPS reset URL from a phone, desktop browser, and a different network; confirm one-time expiry and invalidation of older sessions after reset.
- Obtain external legal approval of Terms and Privacy before marking `PrimeRep-AI/constants/legal-release.json` approved. Verify published document versions match the backend acceptance records (`app/core/legal.py`). Confirm support inbox ownership and response workflow. Check push-provider credentials and the production media domain only for features actually enabled at release.

**Verification:** provider outage and API restart do not silently lose a queued reset email; expired links are never sent as usable links; generic account-discovery behavior remains. A real test account can receive, open, complete, and safely repeat password recovery. Legal status remains pending until actual approval is recorded.

## Phase 4 — Privacy-safe observability and operations

- Instrument backend request failures, latency, readiness, reset-email outbox age/failure, Coach push worker backlog, export errors, and database connection issues. Attach a generated request/correlation ID and release version, but do not include tokens, emails, user identity, raw search terms, exercise questions, notes, or request/response bodies. Keep the existing aggregate catalog timing middleware (`app/main.py`) and extend its pattern to other critical paths.
- Add native crash/error reporting with symbolicated releases and a small set of workout-sync signals: locally queued operation, retry count, age to server acknowledgment, queue depth, finish confirmation, and terminal failure. Report only counts, durations, operation type, platform, app version, and environment. Sending diagnostics must never block logging or replay.
- Use Sentry for exception tracking if a project/account is available, following the current [Expo integration guide](https://docs.expo.dev/guides/using-sentry/). Configure scrubbing before sending events; leave session replay disabled unless separately reviewed. Set alerts for elevated API errors, failed login/reset delivery, growing outbox/queue age, and unusual sync completion failures. Test with synthetic accounts and inspect received payloads.
- Write an operator runbook: dashboard links, alert ownership, on-call contact, first checks, mitigation, and incident record. Include the procedure for a user report of a missing workout, using canonical session IDs and private support tooling without exposing another user's data.

**Verification:** force a safe test exception and known failing request in preview, confirm correctly symbolicated traces and alerts, and inspect that private fields are absent. Simulate Resend/Redis/database downtime and show that alerts identify the affected subsystem. Do not infer “zero data loss” from a quiet dashboard alone.

## Phase 5 — Backup, rollout, and rollback

- Define database backup schedule, retention, encryption, access, and point-in-time recovery under the selected provider. Restore into an isolated database and verify user, session, program, legal-consent, and export records. Record actual recovery time and point; backup configuration without a restore drill does not meet this phase.
- Use additive migrations and backend-first compatibility where possible. Run upgrade and downgrade/upgrade on a disposable database, then rehearse a failed deployment with traffic still on the prior version. For migrations that cannot safely downgrade with real data, document forward repair and the exact cutover boundary.
- Create a release manifest linking backend commit, migration revision, frontend commit/build number, legal versions, catalog release, environment, and operator. Promote a tested preview release to TestFlight and Play internal testing. Roll out gradually, monitor error and sync dashboards, and record a stop/rollback decision if a gate fails. If EAS Update is enabled, verify rollback by channel/runtime version; a database rollback must be handled separately.
- Keep a public launch as a separate decision after the release checklist is green. Store submission needs actual developer accounts and signing credentials; test builds alone do not publish the app. Follow [Expo store build/submission guidance](https://docs.expo.dev/deploy/build-project/) and [PostgreSQL backup/restore guidance](https://www.postgresql.org/docs/current/backup.html).

**Verification:** a restore drill succeeds; the previous compatible app/API version can be reinstated; an intentionally broken preview build is stopped without touching production data.

## Final release gates and handoff

Run backend focused and full suites; migration upgrade/downgrade/upgrade on disposable PostgreSQL; frontend lint, typecheck, UI action audit, Expo web export, Maestro YAML validation, and available simulator/device flows; `git diff --check` in both repositories. Run release-build smoke tests on iOS and Android for signup, login, reset, program activation, offline logging/recovery, Coach, profile edits, export, and account deletion. Test cross-account isolation, a slow network, airplane mode, force-kill, and return from background.

Part 9 engineering is complete only when the required code, deployment recipe, monitoring, restore drill, and release runbook are verified. Production release additionally requires the verified sending/HTTPS domains, rotated credentials, real legal approval, store accounts/signing, and a green preview rollout. Record any unmet gate plainly; do not label a local or simulator-only run as production-ready.
